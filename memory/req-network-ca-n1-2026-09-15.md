## Звуковая модель

Восемь узлов и обратная связь N0. Сначала исправить R1 из ревью: у шестого узла правый маршрут равен нулю и в выходе, и при входе в матрицу. Набор условий N1 сохранён в [fixtures](research/network-n1-fixtures-2026-09-15.json): 44.1 kHz, фиксированные частоты всех банков, исходные параметры узлов, задержка 2064 отсчёта, SVF `q=0.99`, матрица всех межузловых связей без диагонали. Это зафиксированная реконструкция; точное совпадение всей обвязки с Max не заявляется.

Оригинальный `gutterOsc.class` остаётся эталоном шага узла. N0 и прежний `pm_network` сохраняют свои идентификаторы и материалы. Новая маршрутизация и новый маппинг получают явную версию конфигурации; старые файлы N0 не перезаписывать новыми результатами под прежними хешами.

## Поле → звук

Для поля `H×W` разделить строки на 2 части, столбцы на 4. Область `(r,c)`:

`[floor(rH/2), floor((r+1)H/2)) × [floor(cW/4), floor((c+1)W/4))`.

Узлы соответствуют областям слева направо, сверху вниз: `i=4r+c`, `i=0…7`. Для каждой области:

```
n_i = число живых клеток
u_i = n_i / (n_i + 2)
ratio_i = 2 ** clip(log2(scale) + depth * (2*u_i - 1), -1, 1)
freq_ij = min(19000, base_freq_ij * ratio_i)
```

`base_freq_ij` всегда берётся из fixtures, сдвиг не накапливается. Частоты передаются с той же float32-точностью, что сообщения исходному Java-узлу; пересчитываются коэффициенты банка, состояния фильтров и нелинейных узлов сохраняются. Все восемь целей применяются атомарно на границе блока, непосредственно как сообщения исходного управления частотами. Если для устранения установленного артефакта потребуется интерполяция, описать её точную семантику и отдельно повторить сравнение: текущие пробы использовали непосредственную смену коэффициентов.

`depth=0` даёт ручной масштаб банка независимо от поля. Пустое поле означает `n_i=0`; модель продолжает расчёт из текущего состояния. Управление от поля в этом опыте меняет только частоты банков. Эволюция и рисование не сбрасывают сеть. Пауза КА сохраняет живой звук; Stop/Restart следуют существующему транспорту стенда.

## Управление в стенде

| Параметр | Диапазон, по умолчанию | Действие |
|---|---|---|
| `scale`, «Resonators» | 0.5…2, 1 | Общий множитель частот в формуле выше. |
| `depth`, «CA amount» | 0…1, 1 | Глубина влияния поля. |
| `interaction`, «Links» | 0…256, 127 | Штатный общий коэффициент связи `(value/256)^2·5`, ramp 50 ms. |
| `freeze_ca`, «Freeze CA» | 0/1, 0 | Удерживает текущий вектор `u`; ручные параметры продолжают действовать. При выключении берётся текущее поле. |

При init замороженный вектор берётся из начального поля. Показывать границы восьми областей и соответствующие номера узлов поверх поля. Общую громкость использовать существующую. Фиксированный масштаб перед переданным стендом `gain`: 20; по умолчанию это эффективный множитель `20·0.04·0.7=0.56` при `level=1`. Счётчик клиппинга измеряет результат до int16; коэффициент не меняется автоматически от поля или сцены.

## Исходный диагностический опыт (постановка для пользователя отозвана)

Поле 32×32, B3/S23, тор, 2 поколения/с. В столбцах 4, 12, 20, 28 поставить по вертикальному блинкеру в строках 14, 15, 16. Координаты нулевые; готовые списки клеток и ожидаемые векторы приложены в fixtures.

Сторона A — управление от поля; B — `freeze_ca=1`, остальные параметры одинаковы, начальные состояния идентичны. Число клеток при эволюции постоянно — 12; распределение между областями меняется. Пользователь может свободно рисовать и сохранять находки. Краткий текст сцены: «A следует полю, B удерживает начальное управление. Рисуй, запускай эволюцию, сохраняй опыт и заметки».

В fixtures также дано то же поле, сдвинутое на 8 строк, для технической проверки повторных вмешательств; искать специальную фигуру пользователю не нужно.

## Проверки Developer до передачи

1. **Верность модели:** Java-сверка узла; отдельная направленная связь с точным отсчётом прихода; маршрут R6 выключен в обоих местах. Сверка живого вычислительного ядра с медленной моделью на статическом поле, эволюции и повторных правках. Одинаковые команды на одном отсчёте должны означать одинаковое управление; время эволюции округляется по существующим границам блоков стенда.
2. **Влияние поля:** фактические `u` и частоты соответствуют fixtures. С depth=0 либо Freeze CA правки поля не меняют управление. С активным управлением проверить эволюцию и повторный перенос поля туда-обратно без сбросов; сохранить измерения уровней, спектров и временных изменений. Отличие PCM само по себе не считать достаточным результатом.
3. **Живая работа:** текущий Python-рендер медленнее реального времени; требуется ускорить вычисление, сохранив порядок и точность математического шага. На целевой машине две стороны A/B должны устойчиво обрабатываться быстрее длительности блока 352/44100 с; проверить 60 с работы с вмешательствами без опустошения аудиобуфера. Отчёт включает p95/p99 времени блока. Заранее записанный WAV этот пункт не выполняет.
4. **Продолжение опыта:** Save → Continue и воспроизведение совпадают с непрерывным расчётом. Снимок включает кольцевые задержки, узлы, все фильтры, коэффициенты/частоты, ramps, удержанный вектор поля и версию модели. Notes читаются тем же механизмом, что в существующих опытах.
5. **Регрессия:** `python check.py`; отсутствие NaN/Inf и неучтённых сбросов в подготовленных сценариях и при крайних значениях ручек, счётчик перегрузки работает. Старые движки и записи воспроизводятся.
