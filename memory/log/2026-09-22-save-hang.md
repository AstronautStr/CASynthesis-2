# 2026-09-22 — Save больше не морозит инструмент (и работает дольше 30 секунд)

Жалоба пользователя: «синт при нажатии кнопки сейв зависает». Кнопка Save появилась
в тот же день ([лог](2026-09-22-instrument-panel-and-save.md)); здесь — что с ней было
не так и чем это лечится. Работа велась в отдельном worktree `fix/save-hang`.

## Что измерено (до правки)

Прототип гонялся headless (SDL dummy, `CASYNTH_VOLUME=0.01`), по стадиям обёрнуты
`_dump_session` / `scene_from_session` / `offline_record.record` / `Catalog.save`.
Сессия — 60 с игры на стартовых настройках (Laplace+, n 20):

| стадия | время |
|---|---|
| `_dump_session` | 0.05 с |
| `scene_from_session` | 0.05 с |
| **`offline_record.record`** | **27.55 с** |
| итого от клика до ответа | **28.2 с** |

И в конце — `Save failed: offline record: cut 1323168 frames, expected 2706176`.

Два независимых дефекта:

1. **Заморозка.** Весь путь Save шёл В КАДРОВОМ ЦИКЛЕ. Офлайн-рендер стоит примерно
   половину длины сессии (28 с на минуту игры), и всё это время окно не рисуется и не
   отвечает — Windows красит его в «Не отвечает». Снаружи это ровно «зависло».
   Прямой замер отзывчивости (обёртка вокруг `draw_frame`): **0 кадров за 8 с** после клика.
2. **Обрезание на 30 секундах.** `Recorder` держит ПОСЛЕДНИЕ `window_seconds` аудио в
   кольце (живой стенд пишет скользящее окно, дефолт 30 с), а `offline_record.record`
   требует назад ВСЕ кадры рендера. Сессия длиннее 30 с → cut короче ожидаемого →
   `RuntimeError`. То есть после 28 секунд заморозки пользователь получал ещё и ошибку.

## Правка

**`casynth_lab/offline_record.py`** — кольцо рекордера размером с рендер:
`window_seconds=max(WINDOW_SECONDS_DEFAULT, n_blocks * BLOCK / SR)`. Офлайн-сборка — это
не скользящее окно, а весь рендер. Демо-сборки (`build_sn_demos` 8/12 с, `build_n1_demos`
12/20 с) короче 30 с, поэтому у них окно прежнее и записи байт-в-байт те же.

**`gol_synth.py`** — клик Save только ПРИНИМАЕТ РЕШЕНИЕ сохранить:
- `_rec_snapshot(rec)` — поверхностная копия журнала сессии, снятая на ГЛАВНОМ потоке
  (списки копируются, массивы внутри после append никто не трогает: каждый grid кладётся
  `.copy()`). Это микросекунды — всё, что клику позволено стоить. Снимок нужен потому,
  что журнал продолжает расти, пока идёт сохранение, а сцена из логов разной длины — уже
  не та сессия, которую играли.
- `_save_worker` — dump → scene → рендер → `Catalog.save` в своём потоке (`daemon`,
  имя `casynth-save`).
- Прогресс: `on_block` (этот параметр у `record` уже был) пишет долю в `_save_job`;
  тулбар показывает `Rendering 61s 47%`, а `_save_pump()` раз в кадр печатает отметки
  0/25/50/75/100% В КОНСОЛЬ ИЗ ГЛАВНОГО ЦИКЛА — эти строки заодно и есть доказательство,
  что цикл крутится (гейт их и читает).
- Повторный клик во время сохранения: «Save: the previous one is still being written».
- Выход из прототипа `join`-ит воркера — сохранение, начатое перед закрытием, доезжает.

- завершает прототип ПОСРЕДИ рендера — проверяя заодно, что выход дожидается воркера.

Проверено, что гейт ловит каждую половину правки по отдельности (откат одного файла за раз):
- без потока: `[FAIL] only 0 frames drawn in 8s of saving: the save is holding the frame loop`;
- без правки кольца: `[FAIL] Save produced no record` + `Save failed: offline record: cut 1323168
  frames, expected 1585760` (и видно, как выход дождался воркера: `finishing the save before quitting`).

## Чего это стоит живому звуку

Сохранение теперь идёт ПАРАЛЛЕЛЬНО игре, то есть конкурирует за CPU с рендер-тредом.
Замер (один и тот же сценарий 40 с + 30 с, headless): без Save — `1.52 мс/блок, worst 18.66,
underruns 0`; с Save в фоне — `1.31 мс/блок, worst 25.41, underruns 8`, look-ahead сам
вырос с 5 до 12 чанков. То есть несколько пропусков на входе в рендер, дальше играет.
Размен сознательный: восемь андерранов против 28 секунд мёртвого окна.
