# 2026-09-23 — Аудит покрытия тестами: что реально держит звук, а что нет

Запрос пользователя: провести аудит покрытия тестами с упором на НЕОБХОДИМОСТЬ —
не «кнопка нажимается», а «может ли параметр или подсистема аудио-движка изменить
поведение так, что мы не узнаем». Код не менялся: только прогон гейтов, замер и
чтение тестов против кода.

## Для пользователя

- Проверок много и они в основном настоящие: ~490 автотестов плюс 8 скриптовых
  проверок, полный прогон 4 минуты. Звуковой код (17 движков, ядро, стенд) тесты
  исполняют на 93–99 % строк, и почти каждый закон звука сверяется либо с записанным
  байт-в-байт эталоном, либо с независимой эталонной реализацией. Незаметно
  поменять звук движка, не уронив тест, практически нельзя.
- Три реальные дыры, где поведение может уехать незаметно:
  1. Режим перегрузки пула хвостов (плотное поле + длинный release) — код есть,
     его не исполняет ни один тест. Вчерашняя векторизация этого кода заявлена
     «побитово той же», но именно для этих веток это не проверено ничем.
  2. Живой инструмент — то, что слышит игрок, — ни одна проверка не сравнивает
     с офлайн-рендером. Проверяется только «звук есть» и «огибающая двигается».
     Команда сравнения существует, но она ручная и, по записям, расходится.
  3. Стартовые настройки инструмента держит только пиксельная проверка кадра,
     которая уже красная. Их изменение никто не заметит.
- Сам набор проверок как индикатор «зелёный/красный» сейчас не работает: два гейта
  красные постоянно (известно и принято), ещё два в этом прогоне упали от нехватки
  памяти при параллельном запуске и прошли поодиночке. Итог «FAIL» — норма, и
  новая поломка внутри этих гейтов невидима.
- Часть эталонов лежит в файлах, которых нет в git (wav-записи каталогов). На
  чистой копии репозитория эти тесты упадут, хотя хэши записей в git есть.
- Первые три пункта закрываются небольшими тестами (день работы), четвёртый —
  настройкой запуска гейтов. Ничего из этого не требует менять звук.

## 1. Метод

1. Полный `python check.py` как есть (базовое состояние гейтов), затем упавшие
   гейты поодиночке.
2. Замер покрытия по строкам: `coverage.py` 7.16 установлен в scratchpad (в
   окружение проекта не ставился), все 38 гейтов + UI-кадр прогнаны под ним с
   учётом дочерних процессов (пробы прототипа, дочерние стенды S6/S7). Ядра
   numba (`@_jit`) исключены из подсчёта строк — их поведение держат скалярные
   эталоны, см. §3.
3. Главное — не строки, а сила утверждений. Каждый звуковой модуль отнесён к
   категории по самому сильному тесту, который его держит:
   - **A** — версионированный байтовый эталон в git (golden npz, sha256 в
     `record.json`, JSON-хэши);
   - **B** — независимая эталонная реализация или аналитический закон внутри
     теста (скалярная модель, числа preflight, разложение Бесселя);
   - **C** — согласие с самим собой (реплей == рендер, число потоков, Continue
     байт-в-байт): ловит недетерминизм, но НЕ смену закона;
   - **D** — только smoke (запускается, нет NaN, уровень двигается);
   - **E** — ничего.

## 5. Находки по приоритету

### 5.1 HIGH — пул хвостов в перегрузе не исполняется ни одним тестом
`SlotPool._acquire_tail` ветка кражи (пул пуст → крадём самый тихий хвост, счётчик
`steals`) и `_enforce_tail_budget` ветка вытеснения (`over > 0` → fast-fade самых
тихих) — строки 542–546 и 559–565 — не выполняются ни golden master (2 голоса), ни
S1/S2, ни якорями. Это закон «мягкой деградации без щелчка» под плотным полем с
длинным release, ровно то, что игрок делает на Random. Коммит `9849350` (09-22)
переписал обе ветки векторно с заявкой «тот же слот побитово» — для этих веток
заявка не проверена ничем. Ни один тест не читает `pool.steals`.
Закрыть: второй golden-эталон (плотное Random-поле, GEN release ~4 с, 12 пок./с,
~3 с) + утверждение по `steals`/`steal_amp_max`; отдельный npz, старый эталон не
переблессить.

### 5.2 HIGH — живой инструмент не сверяется с офлайн-рендером
Всё, что делает `gol_synth._render_block` и `_render_loop` (когда применяется
поколение, кроссфейд при смене вкладки, VCA, глайд gain, кольцо), держат только
пробы уровня «звук есть». `ui_save_probe` доказывает «запись реплеится байт-в-байт»,
но это офлайн против офлайн. Единственная сверка live↔offline — ручной
`python gol_synth.py scene <ts>` (0 % покрытия), и по логу 09-22 она расходится с
первого ручного изменения поля. Кроссфейд двух экземпляров движка при смене
вкладки под звуком не проверяет никто (click-проба только «выжил»).
Закрыть: гейт «сессия без ручных правок поля» (Random → Play → нота → одна ручка
→ смена вкладки, 6 с, `CASYNTH_RECORD=1`) с побайтовым (или ≤ 1 LSB, если
таймлайн ручек кладётся на кадр) сравнением live WAV и офлайн-рендера сцены.
Расхождение при ручных правках — отдельная известная задача.

### 5.3 HIGH — набор гейтов не даёт честного «зелёный/красный»
- Два постоянно красных гейта (`live budget` Ev+FM, `ui frame`) → итог всегда FAIL →
  регрессии внутри них невидимы. Варианты: явный expected-fail с причиной (гейт
  сообщает «красный как и ожидалось» и краснеет заново только при НОВОМ падении),
  либо переблессить кадр на устройстве пользователя, либо снять Ev+FM с
  потолка до решения Researcher.
- Параллельная волна роняет гейты по памяти (S7, articulation в этом прогоне).
  `DEFAULT_JOBS = min(6, cpu//3)`; на 16 ГБ шесть процессов с пулами таблиц и
  дочерними прототипами не помещаются. Закрыть: пометить тяжёлые по памяти гейты
  (пробы прототипа, S7) и гнать их не более двух одновременно, либо `--jobs=3`
  по умолчанию на этой машине.
- Первый прогон после правки jit-функции падает в гонке компиляции numba (память
  09-22) — прогреть кэш одним процессом до волны.
- Пересечение с `memory/audit-infra-2026-09-22.md` (не закоммичен): там уже предложен
  список `EXPECTED_RED` в `check.py` (P1.3) — это и есть ответ на первый пункт. Но его
  P3.12 («попробовать `--jobs=8` на 20 ядрах») этим прогоном опровергнут: узкое место —
  не ядра, а память; уже при 6 процессах два гейта упали по `Out of memory`.

### 5.4 MEDIUM — пины записей зависят от wav, которых нет в git
`rendered_like` (наборы Birth strength, Decay law) сравнивает текущий рендер со
стороженным `monitor.wav`/`A.wav`/`B.wav`; wav в `.gitignore`, `rec.pcm` без
файла бросает `CatalogError` → на чистой копии репозитория эти тесты ПАДАЮТ (не
skip). N4/Objects-Laplace в том же случае тихо skip-ают (пин исчезает). При этом
`record.json` уже хранит `sha256` каждого выхода — `test_laplace_fm.Records`
сравнивает именно с ним. Закрыть: сверять хэш из `record.json`, wav — только если
есть.

### 5.5 MEDIUM — стартовая позиция инструмента держится красным гейтом
`START_SPECTRUM` / `DEFAULT_ENGINE` / наложение на все движки с полным спектром
(`_start_params`) проверяет только пиксельный кадр, который красный и не блессится
по решению пользователя. `events_master.py` копирует значения руками, не
импортирует. Закрыть: 20-строчный тест — `_start_params(eid)` для каждого
playable движка равен дефолтам реестра с наложенным `START_SPECTRUM` там и только
там, где есть все семь ключей; `DEFAULT_ENGINE` playable.

### 5.6 MEDIUM — переполнение пула таблиц волн
Политика «низкие частоты обслуживаются первыми, остальные моды читаются как
синус» проверена только на «не падает». Это меняет звук в перегрузе (драг `harm`
на плотном поле). Пока REQ carriers §9 не решён Researcher-ом — хотя бы маленький
синтетический пин: пул на N строк, N+k частот → ровно k верхних мод помечены −1.

### 5.7 LOW
- `_on_midi_message`: тест с синтетическими сообщениями mido (note_on/off, last-note,
  onset, gate при отпускании последней) — без девайса.
- Живой путь `tune`: `_snap_note_on` со спектром колонии → `tuned_f0`; сейчас снап
  ни разу не исполняется тестом.
- `AudioHost.reopen` + `audio_choice_save`: dropdown прототипа; «нет звука» было.
- `reset()` ни одного движка не зовётся тестами (контракт «== init на том же поле»).
- Единый снапшот-тест таблицы реестра (17 движков → JSON в `tests/golden/`): сейчас
  проверяется по кускам в 8 наборах.
- `casynth_session.replay_session`/`_replay_cli` (0 %, superseded сценой) — удалить,
  а не тестировать. Мёртвые скрипты корня — либо 1-секундный import-smoke гейт,
  либо `archive/` (`ab_bench.py` назван в `current.md` инструментом слуховой очереди
  tune/fullshape и не запускался с июля).

**(a) Пул хвостов в перегрузе — гейт 2b `tests/golden/tail_pool_master.py` (коммит `ffa8543`).**

**(b) Живой инструмент == офлайн-рендер — гейт 3g `tests/ui_fidelity_probe.py`.**
Headless-сессия прототипа (Random → Play → клавиша, 13 поколений, `CASYNTH_RECORD=1`) →
`scene_from_session` (тот же путь, что Save) → офлайн-рендер стендом → побайтовое сравнение с
записанным WAV. До работы: 41.7 % и 5.2 % совпадающих семплов, max|diff| до 949 LSB, первое
расхождение на первом звучащем блоке. Две причины, обе найдены экспериментом:
1. **Семантика ручной правки поля.** Стенд на `set_cells`/`clear` подаёт движку
   `events_field(prev, new)`, прототип `exc_field` на правке не трогает. На стартовых настройках
   (`dyn` 1) офлайн был в 2.7 раза громче первую секунду. Дизайн-вопрос — `memory/questions.md`
   [OPEN] 2026-09-23; до решения проба рендерит по семантике прототипа (шим в тесте).
   **Следствие для Save сегодня:** при `dyn` > 0 запись каталога звучит не так, как звучал инструмент.
2. **Расстановка правок из кадрового лога.** `scene_from_session` ставил `set_cells` на семпл, где
   был поток рендера в момент записи кадра; потоки гоняются на ±1 блок, и правка попадала на блок
   раньше применения (кадр 14784, применено 15136). Мода, стартовавшая на блок позже, несёт сдвиг
   фазы навсегда — разница не сходилась. Исправлено в `casynth_session.py`: правка ставится на
   строку `field_applied` (поток рендера пишет её и для правок, не только для шагов; строка без
   приращения шагов = правка; ближайшая в пределах ±2 блоков, по порядку). Это же чинит записи Save.
